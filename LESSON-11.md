## Шаг 1. Predict — сначала предсказываем (10 минут)

### Что мы собираемся сделать

Сейчас ваша страница умеет завершать **первую** задачу — ту, что стоит в `tasks[0]`. Сегодня мы заменим кнопку «Завершить первую задачу» на **две** вещи: **список выбора** и кнопку «Завершить выбранную задачу». Пользователь выбирает задачу — программа завершает её.

> **Важно: сначала предсказание, потом запуск.** В этом шаге мы **ничего не выполняем** — ни одной строки в консоли, ни одной строки в файле. Мы только **записываем** то, что, по нашему мнению, произойдёт. Проверять будем в шаге Run.

### Главная модель урока

Всё, что мы сегодня сделаем, укладывается в одну цепочку:

**Выбор → определение задачи → изменение состояния → обновление списка.**

Читается она так: **пользователь выбрал вариант в списке** (выбор) → **страница сообщила его номер** (определение задачи) → **изменилось поле `done` у выбранной задачи** (изменение состояния) → **список перерисовался** (обновление списка).

Обратите внимание: сама операция «завершить задачу» нам уже знакома из Урока 10. Новое здесь — только **шаг выбора**: какая именно задача будет затронута.

### Новое понятие урока: `<select>` и `selectedIndex`

**`<select>`** — это элемент HTML, который показывает пользователю **список вариантов** и позволяет выбрать **один** из них. Это «выпадающий список» — самый обычный способ спросить человека «какой из вариантов тебе нужен?».

У `<select>` есть **одно** свойство, которое нам нужно:

**`selectedIndex`** — это **номер позиции** выбранного варианта, считая с нуля.

| Позиция | Что выбрано |
|---:|---|
| `0` | первый вариант |
| `1` | второй вариант |
| `2` | третий вариант |
| `-1` | **ничего не выбрано** |

> **`selectedIndex` — это уже число.** Браузер сам отдаёт его числом. Никаких `Number()`, никакого разбора строк — **не нужно**.

## Шаг 2. Run — делаем выбор и кнопку (15 минут)

### 1. Замените кнопку на список выбора и новую кнопку

В блоке «Задачи» замените **старую** кнопку `#complete-first-task` на **новую** разметку — список выбора и кнопку:

```html
<section>
  <h2>Задачи</h2>
  <label for="task-choice">Выберите задачу:</label>
  <select id="task-choice"></select>
  <button id="complete-selected-task">
    Завершить выбранную задачу
  </button>
  <ul id="task-list"></ul>
  <p>Всего задач: <span id="task-count">—</span></p>
</section>
```

Что здесь нового:

| Строка | Зачем она |
|---|---|
| `<label for="task-choice">Выберите задачу:</label>` | **подпись** для списка выбора. Атрибут `for` говорит браузеру, к какому элементу она относится |
| `<select id="task-choice"></select>` | сам **список выбора**. Сейчас он пустой — варианты добавим из данных на следующем шаге |
| `<button id="complete-selected-task">` | **новая** кнопка. Она завершает **выбранную** задачу, а не первую |

> **Старую кнопку `#complete-first-task` уберите.** Она больше не нужна: сегодня у нас **одна** кнопка завершения, и она завершает **выбранную** задачу. Если оставить обе — на странице будет две кнопки, которые делают разное, и понять, какая чем занимается, станет трудно. Заодно удалите из JavaScript функцию `completeFirstTask()` и её подписку — они больше не вызываются.

### 2. Напишите функцию, которая заполняет список выбора

Добавьте в свой файл **отдельную функцию** — рядом с `renderTaskList()`. Она строит варианты выбора **из массива**:

```javascript
function renderTaskChoices() {
  const select = document.querySelector('#task-choice');

  if (!select) {
    console.error('Не найден выбор задачи');
    return;
  }

  select.textContent = '';

  for (const task of tasks) {
    const option = document.createElement('option');
    option.textContent = task.title;
    select.appendChild(option);
  }
}
```

Что здесь происходит — **по порядку**:

| Строка | Зачем она |
|---|---|
| `const select = document.querySelector('#task-choice');` | находим список выбора на странице — тот же приём, что и раньше |
| `if (!select) { console.error(...); return; }` | **защита**: если списка на странице нет, **говорим об этом** и **выходим**. Страница не должна падать |
| `select.textContent = '';` | **очищаем** список вариантов перед заполнением — как мы очищали список задач в Уроке 09 |
| `for (const task of tasks)` | **тот же цикл**, что и в `renderTaskList()` — проходим по всем задачам |
| `document.createElement('option')` | создаём **один** вариант выбора для каждой задачи |
| `option.textContent = task.title;` | текстом варианта делаем **название задачи** — прямо из данных |
| `select.appendChild(option);` | добавляем вариант в список выбора |

> **Почему варианты строятся из данных, а не пишутся руками.** Если мы напишем три `<option>` вручную, то при добавлении четвёртой задачи список выбора останется прежним — и программа «не увидит» новую задачу. Список, построенный циклом, **всегда** совпадает с массивом: одна задача — один вариант.
>
> **Обратите внимание на сходство с `renderTaskList()`.** Это **тот же** приём: создаём элемент, пишем в него текст, добавляем в конец. Сегодня мы применяем уже знакомый приём к **новому** элементу — `<option>`.


### 3. Напишите функцию, которая завершает выбранную задачу

Теперь — главная функция урока. Заметьте, как она отличается от `completeFirstTask()` из Урока 10:

```javascript
function completeSelectedTask() {
  const select = document.querySelector('#task-choice');

  if (!select) {
    console.error('Не найден выбор задачи');
    return;
  }

  const index = select.selectedIndex;

  if (index < 0 || index >= tasks.length) {
    console.error('Задача не выбрана');
    return;
  }

  tasks[index].done = true;
  renderTaskList();
}
```

Что здесь происходит — **по порядку**:

| Строка | Зачем она |
|---|---|
| `const select = document.querySelector('#task-choice');` | находим список выбора |
| `if (!select) { console.error(...); return; }` | **защита**: элемента нет — говорим об этом и выходим |
| `const index = select.selectedIndex;` | **определяем задачу**: спрашиваем у браузера номер выбранной позиции |
| `if (index < 0 || index >= tasks.length)` | **вторая защита**: если ничего не выбрано (`-1`) или номер вышел за границы — **выходим** и пишем в консоль понятное сообщение |
| `tasks[index].done = true;` | **изменение данных**: у **выбранной** задачи состояние становится «выполнена» |
| `renderTaskList();` | **показ**: явно говорим странице показать список заново, с новым состоянием |

> **Главное отличие от Урока 10.** Там было `tasks[0].done = true;` — индекс **зашит** в код. Сегодня `tasks[index].done = true;` — индекс **приходит** от пользователя. Всё остальное — та же операция: изменить состояние и явно обновить показ.
>
> **Зачем проверка `index < 0`?** Если ничего не выбрано, браузер вернёт `-1`. А `tasks[-1]` — это `undefined`, и строка `tasks[-1].done = true` упала бы с ошибкой. Поэтому мы **проверяем** и **выходим**. Это тот же приём защиты, что и `tasks.length === 0` в Уроке 10, только для номера.
>
> **Почему не нужно `Number()`?** `selectedIndex` — уже число. Превращать его в строку и обратно было бы лишним шагом.

### 4. Подключите всё в уже знакомом месте

В том же месте, где вы в Уроке 10 вызвали `renderTaskList()` (в Уроке 08 это `startCounter()`), сделайте **три** вещи, **в этом порядке**:

```javascript
  renderTaskChoices();
  renderTaskList();

  const completeButton = document.querySelector('#complete-selected-task');

  if (!completeButton) {
    console.error('Не найдена кнопка завершения задачи');
  } else {
    completeButton.addEventListener('click', completeSelectedTask);
  }
```

| Что | Зачем |
|---|---|
| `renderTaskChoices();` | **один** раз заполняем список выбора из данных |
| `renderTaskList();` | **один** раз строим список задач, как в Уроке 09 |
| `addEventListener('click', completeSelectedTask)` | **одна** подписка: при клике вызывается наша функция |

> **Где именно подключать.** Подписка — **один раз** при загрузке, в существующей функции инициализации. **Не** внутри `renderTaskList()` и **не** внутри `renderTaskChoices()`: иначе при каждом показе на кнопку добавлялся бы ещё один обработчик, и одно нажатие вызывалось бы функцией несколько раз. Это **то же** правило, что в Уроке 10.

## Шаг 3. Investigate — разбираем, что произошло (15 минут)

### Цепочка целиком

Когда вы нажали кнопку, произошло ровно пять вещей, **по порядку**:

1. **Выбор.** Пользователь выбрал второй вариант в списке `#task-choice`.
2. **Определение задачи.** Страница прочитала `select.selectedIndex` — получила число `1`.
3. **Поиск объекта.** `tasks[1]` — это второй объект-задача в массиве.
4. **Изменение состояния.** Выполнилось `tasks[index].done = true;` — изменилось поле `done` **у выбранной** задачи.
5. **Обновление списка.** Вызвалась `renderTaskList()` — список перерисовался, и во втором пункте появилось «— Выполнена».

### Почему порядок вариантов должен совпадать с порядком задач

Это **ключевой** вопрос урока. Смотрите:

| Позиция в `<select>` | Какой `<option>` создан | Какой элемент массива |
|---:|---|---|
| `0` | первый созданный `<option>` | `tasks[0]` |
| `1` | второй созданный `<option>` | `tasks[1]` |
| `2` | третий созданный `<option>` | `tasks[2]` |

`renderTaskChoices()` идёт по массиву **в том же порядке**, в котором создаёт варианты. Поэтому «второй вариант» и `tasks[1]` — это **одно и то же** задание.

> **Что будет, если порядки разойдутся?** Если бы мы создавали варианты в обратном порядке, то выбор «Прочитать главу» (позиция `0`) означал бы `tasks[2]`. Человек выбрал «главу» — а программа завершила «результат». Ошибка была бы **незаметна**: никакой ошибки не возникло бы, страница просто показала бы не то. Поэтому совпадение порядков — это не украшение, а **условие правильной работы**.

### Сравните с Уроком 10

| | Урок 10 | Урок 11 |
|---|---|---|
| Что выбирает пользователь | ничего | **задачу** из списка |
| Откуда берётся индекс | `tasks[0]` — **зашит** в код | `select.selectedIndex` — **приходит** от браузера |
| Какая задача меняется | всегда первая | **та, которую выбрали** |
| Операция | изменить состояние + показать | та же самая |

> **Что изменилось, а что нет.** Изменился **только** один шаг — **как мы узнаём номер задачи**. Операция «изменить `done` и вызвать `renderTaskList()`» осталась ровно той же, что в Уроке 10. Это и есть признак хорошего урока: новое понятие добавляется **поверх** знакомого кода, а не ломает его.

### Данные и показ — по-прежнему две разные операции

Мы **выбрали** задачу — это **выбор**. Мы **изменили** `done` — это **изменение данных**. Мы **вызвали** `renderTaskList()` — это **показ**.

Выбор сам по себе **ничего** не меняет в данных. Пользователь может сколько угодно переключать варианты — пока он не нажал кнопку, **ни одна задача** не изменится. Изменение начнётся только после нажатия.

### Что такое идемпотентность и почему она здесь

Нажали кнопку два раза с одним и тем же выбором — результат **не испортился**. Это свойство называют **идемпотентностью**.

**Идемпотентная операция** — это операция, которую можно выполнить повторно, и результат останется тем же. Повторное «завершить задачу» не создаёт **нового** изменения: задача и до повтора была выполненной, и после — выполненная. Состояние просто **уже было** `true`, и мы записали `true` ещё раз.

> **Если выбранная задача уже была выполнена**, кнопка ничего не испортит: она запишет `true` в `true` и перерисует список. Тот же результат.


...а потом нажмите кнопку. Что произойдёт?

Правильный ответ: **ничего не сломается**. Функция увидит `index === -1`, напишет в консоль «Задача не выбрана» и **выйдёт**. Ни одна задача не изменится, список останется прежним.

> **Почему это важно.** «Задача не выбрана» — это **штатная** ситуация, а не поломка. Программа обязана вести себя вежливо: сказать, что не так, и **не** менять данные.

## Шаг 4. Modify — выбираем другую задачу (15 минут)

### Что мы собираемся сделать

Мы завершали **вторую** задачу. Теперь выберем **третью** и посмотрим, что изменится. Код трогать **не нужно** — меняется только **выбор** в списке.

### Запишите предсказания ДО запуска

1. Какая задача изменится? ___
2. Что будет с первой задачей? ___
3. Что будет со второй задачей (той, что мы завершали раньше)? ___
4. Сколько будет пунктов в списке? ___
5. Что будет в строке «Всего задач»? ___

### Выполните

1. Выберите **третий** вариант («Проверить результат»).
2. Нажмите «Завершить выбранную задачу».

### Проверьте

| Что | Ожидаемо |
|---|---|
| Первая задача | осталась «— Не выполнена» |
| Вторая задача | осталась «— **Выполнена**» — мы её не трогали |
| Третья задача | стала «— **Выполнена**» |
| Пунктов в списке | ровно **три**, без дублей |
| «Всего задач» | `3` — задач не добавилось, изменилось только состояние |

> **Почему вторая задача осталась выполненной.** Мы выбрали **третью** — значит, программа получила `index === 2` и изменила `tasks[2]`. Про `tasks[1]` она вообще не знала: выбор — это **указание**, а не «сброс всех остальных».

### Проверьте идемпотентность

Теперь выберите **третью** задачу **снова** и нажмите кнопку ещё раз.

Ожидаемо: **ничего не изменится**. Задача и так была выполнена, а `done = true` — это **установка** значения, а не переключение. Она не превратит `true` обратно в `false`.

### Верните как было

Восстановите исходное состояние задач, как в Уроке 10: в файле у всех трёх задач должно быть `done: false`, в списке — три пункта «— Не выполнена», «Всего задач» — `3`. Сохраните файл, обновите страницу и убедитесь, что всё вернулось.

## Шаг 5. Make — своя функция (необязательно, 10–15 минут)

> **Этот шаг необязательный.** Он не входит в критерий завершения урока и **не является условием для Урока 12**. Если времени нет — пропустите его и переходите к проверке.

**Задача.** Опишите, **как** вы бы добавили поддержку **четвёртой** задачи, и проверьте свой ответ.

**Подсказка (если совсем не получается).** Ничего сложного: добавьте в **массив `tasks`** ещё один объект — с новым `title` и `done: false`. Больше **ничего** менять не нужно: `renderTaskChoices()` и `renderTaskList()` оба проходят по массиву циклом.

**Проверьте так:**

1. Добавьте четвёртую задачу в массив `tasks` **в файле**.
2. Сохраните файл и обновите страницу (`F5`).
3. В списке выбора должно быть **четыре** варианта, а в списке задач — **четыре** пункта.
4. Выберите **четвёртый** вариант и нажмите кнопку — должен завершиться **четвёртый** пункт, а не первый и не второй.
5. «Всего задач» должно показать `4`.
6. **Верните** массив к трём задачам, сохраните и обновите страницу.

> **Чего от вас НЕ требуется.** Не нужно писать новый обработчик, придумывать уникальные идентификаторы задач, добавлять сохранение данных или менять что-либо ещё. В этом уроке набор задач меняется только **в файле** — и всё, что нужно, происходит само.

> **На заметку.** В этом уроке мы **не** делаем автоматическую синхронизацию списка выбора с массивом во время работы страницы. Если в будущем коллекция задач начнёт меняться **динамически** (например, появится кнопка «добавить задачу»), то список выбора нужно будет **обновлять** в том же месте, где меняется массив. Мы записываем это здесь, чтобы не потерять: **данные и элементы управления должны обновляться вместе**.

## Что вы теперь умеете

| Раньше | Теперь |
|---|---|
| Кнопка всегда завершала **первую** задачу | Пользователь **выбирает** задачу, и завершается именно выбранная |
| Номер задачи был **зашит** в код (`tasks[0]`) | Номер задачи **приходит** от страницы (`select.selectedIndex`) |
| Список вариантов не существовал | Список вариантов **строится из данных** — циклом, как список задач |
| Понятия «выбор» не было | `<select>` — это выбор, `selectedIndex` — его номер |
| Операция «изменить и показать» была новой | Операция «изменить и показать» **осталась той же** — изменился только выбор |

**Что осталось на потом.** Сегодня мы научились выбирать **какую** задачу завершать. Урок 12 научит **формулировать** правила поведения программы: что операция обещает и что обязана сохранить. Сначала — простыми словами и проверками, потом — формальными контрактами.

## Источники подхода

Урок построен по схеме **PRIMM** (Predict → Run → Investigate → Modify → Make): [primmportal.com](https://primmportal.com/). Шаги Predict и Modify учат связывать выбор с наблюдаемым результатом и предсказывать состояние до изменения; порядок «сначала предсказать, потом запустить» опирается на исследования чтения и трассировки кода новичками (Busjahn & Schulte, 2013; Lister et al., 2004, 2009), перечисленные на странице [Research](https://primmportal.com/research/).

Идея урока — **последовательное усложнение одного и того же проекта**: ученик не переписывает приложение, а меняет **один** шаг в уже работающей операции — вместо зашитого `tasks[0]` появляется номер, выбранный человеком. Это соответствует позиции курса: переход от «программа решает за пользователя» к «пользователь выбирает объект, а программа выполняет операцию» — обычная инженерная задача, и навык «связать элемент управления с данными» важнее, чем новая синтаксическая конструкция. Различение «наблюдения», «проверки контракта» и «формального доказательства» соответствует подходу курса (см. [CURRICULUM-DESIGN.md](CURRICULUM-DESIGN.md), раздел D.1a). Идемпотентность рассматривается здесь как **наблюдаемое свойство** конкретной операции, а не как формальная спецификация.
