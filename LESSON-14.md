## Шаг 1. Predict — что вообще меняет функция (10 минут)

### Что мы собираемся сделать

В Уроке 13 вы написали функцию `transitionTask(index, event)`. Она работает и у неё **ровно** одно правило — **одна таблица переходов на шесть строк**. Сегодня мы **не меняем** это правило. Мы меняем **расположение** правила: выносим его в отдельную функцию, которая **ничего не меняет**.

> **Важно: сначала предсказание, потом код.** В этом шаге мы **ничего не выполняем** — ни одной строки в консоли, ни одной строки в файле. Мы только **записываем** ответы. Проверять будем в шаге Run.

### Главная модель урока

Сегодняшний урок — про **две** разные цепочки. Первая — та, что у вас уже была:

**Событие интерфейса → вычисление → изменение состояния приложения → отображение.**

Это цепочка **всей** программы: нажали кнопку → программа посчитала → данные изменились → список перерисован.

А сегодня мы **выделим** из неё **средний** кусок и рассмотрим его отдельно:

**Входные данные → вычисление → новые данные.**

Здесь нет ни события, ни страницы, ни показа. Есть только: **что на входе** → **что посчиталось** → **что получилось**. И главное свойство этого куска: **исходные данные при этом не меняются**.

### Таблица переходов — она остаётся прежней

Сегодняшний урок **не меняет** правил. Таблица переходов Урока 13 остаётся **в силе один в один** — мы просто вынесем её в отдельную функцию:

| Текущее состояние | Событие | Результат | Принято? |
|---|---|---|---|
| `new` | `START` | `in_progress` | `true` |
| `new` | `COMPLETE` | без изменений | `false` |
| `in_progress` | `START` | без изменений | `false` |
| `in_progress` | `COMPLETE` | `done` | `true` |
| `done` | `START` | без изменений | `false` |
| `done` | `COMPLETE` | `done` | `true` |

> **Шесть строк — как и было.** Одна таблица переходов на шесть строк. Сегодня она станет **содержимым** чистой функции, но сами **строки** не изменятся.

### Что делает `transitionTask()` из Урока 13

Вот она — целиком, как вы её написали:

```javascript
function transitionTask(index, event) {
  if (!Number.isInteger(index) || index < 0 || index >= tasks.length) {
    return false;
  }

  const task = tasks[index];

  if (task.status === 'new' && event === 'START') {
    task.status = 'in_progress';
    return true;
  }

  if (task.status === 'in_progress' && event === 'COMPLETE') {
    task.status = 'done';
    return true;
  }

  if (task.status === 'done' && event === 'COMPLETE') {
    return true;
  }

  return false;
}
```

### Короткий ответ (после того, как записали своё)

Вот ключевая мысль, из которой вырастет весь урок:

> **Функция, которая меняет данные, вынуждена сообщать о своём результате косвенно — через сами данные.** Она не может просто «вернуть следующее состояние»: она **записывает** его в чужой объект. Если вызвать её дважды — второй вызов увидит уже **изменённое** состояние и посчитает по-другому.

А чистая функция **возвращает** результат и **ничего не меняет**. Её можно вызвать сколько угодно раз — и каждый раз получить **тот же** результат.

> **Внимание, обратная сторона.** Функция, которая **что-то возвращает**, ещё **не обязана** быть чистой. Старая `transitionTask()` тоже возвращала `true` — и при этом **меняла** данные. «Возвращает значение» — это **не** признак чистоты. Признак чистоты — **другое**: функция не трогает ни свои входы, ни всё вокруг.

### Самый короткий путь к первому рабочему примеру

Если хотите увидеть разницу **прямо сейчас**, не читая дальше, — вот он. Введите в консоли браузера:

```javascript
const firstTask = { title: 'Прочитать главу', status: 'new' };

const firstResult = { title: firstTask.title, status: 'in_progress' };

console.log('исходная задача:', firstTask);
console.log('новый результат:', firstResult);
```

Что вы увидите: `исходная задача` по-прежнему `{ title: 'Прочитать главу', status: 'new' }` — **ничего не изменилось** — а `новый результат` — отдельный объект со `status: 'in_progress'`. Это и есть главная идея урока в **четырёх строках**: **можно посчитать новое состояние, не трогая старое**.

## Шаг 2. Run — пишем чистую функцию (15–20 минут)

### 1. Новая функция: `nextTask(task, event)`

Сейчас в вашем коде есть одна функция, которая **и решает**, и **меняет**. Мы разделим её на две.

Сначала — та часть, которая **только решает**. Она принимает **задачу** (объект) и **событие** (строку), а возвращает **решение**: объект с двумя полями — `accepted` (принято ли событие) и `task` (какая задача получается).

```javascript
function nextTask(task, event) {
  if (task.status === 'new' && event === 'START') {
    return {
      accepted: true,
      task: { title: task.title, status: 'in_progress' }
    };
  }

  if (task.status === 'in_progress' && event === 'COMPLETE') {
    return {
      accepted: true,
      task: { title: task.title, status: 'done' }
    };
  }

  if (task.status === 'done' && event === 'COMPLETE') {
    return {
      accepted: true,
      task: { title: task.title, status: 'done' }
    };
  }

  return {
    accepted: false,
    task: { title: task.title, status: task.status }
  };
}
```

Разберём по строкам:

| Строка | Что делает |
|---|---|
| `function nextTask(task, event)` | Новая функция. Принимает **задачу** и **событие** — и **ничего больше** |
| `if (task.status === 'new' && event === 'START')` | Первая строка таблицы переходов: `new` + `START` |
| `accepted: true` | Событие **принято** |
| `task: { title: task.title, status: 'in_progress' }` | **Новый** объект-задача с новым состоянием. Название — **то же самое** |
| `if (task.status === 'in_progress' && event === 'COMPLETE')` | Четвёртая строка таблицы |
| `if (task.status === 'done' && event === 'COMPLETE')` | Шестая строка таблицы — особая: принято, но состояние прежнее |
| `return { accepted: false, task: { … } }` | **Отказ**: событие из этого состояния запрещено. Состояние — **прежнее** |

> **Что здесь принципиально нового.** Раньше вы писали `task.status = 'in_progress';`. Теперь вы пишете `status: 'in_progress'` **внутри нового объекта**. Разница огромная: старая строка **меняла** чужой объект, новая — **описывает** новый объект. Старый объект остаётся **как был**.
>
> Обратите внимание: `task` внутри функции — это **аргумент**, а не «та задача из `tasks`». Функция получила задачу **в руки** и работает только с ней.

### 2. Про границу модели данных

Наша задача — это объект **ровно с двумя** полями: `{ title, status }`. Поэтому мы копируем **именно эти два** поля, явно и по имени:

```javascript
{ title: task.title, status: 'in_progress' }
```

Мы **не** используем ни spread-оператор (`...`), ни библиотеки для копирования, ни вложенных структур. Это **намеренно**: у модели данных ровно два поля, и написывать их по имени — **проще всего и надёжнее всего**.

> **А если полей станет больше?** Если завтра у задачи появится третье поле (например, `priority`), то **правило копирования придётся пересмотреть**: новую задачу придётся создавать со **всем** набором полей. Это нормально: правило копирования — часть контракта модели данных. Пока полей два — пишем два.

### 3. Про отказ: почему мы тоже возвращаем объект

В строке отказа мы написали `task: { title: task.title, status: task.status }` — то есть **новый** объект с **теми же** значениями. Можно ли было вернуть **исходный** объект как есть?

Можно. И это было бы **правильно**: если ничего не меняется, незачем создавать копию. Мы выбрали новый объект просто потому, что так **виднее**: результат всегда одной формы. Обе версии удовлетворяют контракту.

> **Точное правило.** Чистота — это **не** «обязательно создать новый объект». Чистота — это «**не изменить** то, что передали, и **не** менять ничего вокруг». Если ничего менять не нужно — можно вернуть **тот же** объект. Но **нельзя** отдать наружу объект, который потом кто-то **изменит** и сломает исходные данные.

### 4. Теперь `transitionTask()` — тонкая обёртка

Заменяем старую функцию на новую. Она **не решает**, а **применяет** решение:

```javascript
function transitionTask(index, event) {
  if (!Number.isInteger(index) || index < 0 || index >= tasks.length) {
    return false;
  }

  const currentTask = tasks[index];
  const result = nextTask(currentTask, event);

  if (!result.accepted) {
    return false;
  }

  tasks[index] = result.task;
  return true;
}
```

Разберём по строкам:

| Строка | Что делает |
|---|---|
| `if (!Number.isInteger(index) \|\| …)` | **Защита**: тот же вход, тот же отказ, что и в Уроке 13 |
| `const currentTask = tasks[index];` | **Читаем** текущую задачу. Никаких изменений |
| `const result = nextTask(currentTask, event);` | **Просим решение** у чистой функции. Она ничего не меняет |
| `if (!result.accepted) { return false; }` | **Отказ**: событие запрещено из этого состояния. Ничего не меняем |
| `tasks[index] = result.task;` | **Единственное** место, где приложение **меняет** данные. Записываем **результат** |
| `return true;` | Событие **принято** |

> **Почему это правильно.** Правила переходов теперь живут **в одном месте** — в `nextTask()`. `transitionTask()` **не знает** ни про какие состояния: она только спрашивает, принято ли событие, и, если да, кладёт результат на место. Одна функция **владеет** правилами; вторая — **применяет** решение.

> **Что НЕ изменилось.** Сигнатура `transitionTask(index, event)` — та же. Возвращаемое значение — то же (`true` / `false`). `completeSelectedTask()` — **не трогаем** вообще: она по-прежнему вызывает `transitionTask(select.selectedIndex, 'COMPLETE')` и по-прежнему вызывает `renderTaskList()` после успеха.

### 5. Проверьте, что всё работает

Обновите страницу и проверьте то же, что проверяли в Уроке 13. Кнопка «Завершить выбранную задачу» должна вести себя **точно как раньше**.

Теперь проверьте в консоли **новое** — чистоту. Выполните:

```javascript

const pureResult = nextTask(pureInput, 'START');

console.assert(pureInput.status === 'new', 'Исходная задача не должна измениться');
console.assert(pureResult.accepted === true, 'Событие должно быть принято');
console.assert(pureResult.task.status === 'in_progress', 'Должно получиться in_progress');
console.assert(pureResult.task.title === 'Прочитать главу', 'Название должно сохраниться');
```

> **Обратите внимание на первую проверку.** `pureInput` — это **ваш** объект, созданный вручную. Никакой функции приложения к нему не обращалось. И после вызова `nextTask()` у него **всё ещё** `status: 'new'`. Это и есть чистота: **входные данные не изменились**.

А теперь сравните с прежним поведением:

```javascript
const changedTask = { title: 'Прочитать главу', status: 'new' };
changedTask.status = 'in_progress';
console.log(changedTask.status);
```

Здесь мы **сами** изменили объект — и теперь `changedTask.status` равен `in_progress`. Это **старый** способ: чтобы «получить следующее состояние», объект приходилось **переписывать**.

| Способ | Что происходит с исходным объектом | Как узнать результат |
|---|---|---|
| **Старый** (`task.status = …`) | **изменяется** | «посмотри на объект после вызова» |
| **Новый** (`nextTask()`) | **не изменяется** | «прочитай **возвращённое** значение» |

### 6. Одно место, а не два

Проверьте, что в вашем файле **нет** второй реализации правил. Поищите по файлу строки `task.status = ` — внутри `transitionTask()` их **больше нет**. Все присваивания `status` теперь стоят **только** внутри `nextTask()`, и даже там это не присваивание, а **создание** нового объекта.

Если найдёте ещё одну копию правил — удалите её. Две реализации таблицы переходов — это два источника правды, а мы в Уроке 12 уже решили, что источник правды должен быть **один**.

## Шаг 3. Investigate — сравниваем два способа (15 минут)

### Три варианта, которые надо различать

| Вариант | Что делает | Меняет ли исходные данные? |
|---|---|---|
| **Старый** `transitionTask()` (Урок 13) | сама решает и сама меняет `tasks[index].status` | **да** |

Заполните её для **каждой** из шести строк таблицы переходов. Выполните в консоли браузера (после `F5`, чтобы состояния были исходными):

```javascript
const cases = [
  { task: { title: 'А', status: 'new' }, event: 'START' },
  { task: { title: 'А', status: 'new' }, event: 'COMPLETE' },
  { task: { title: 'А', status: 'in_progress' }, event: 'START' },
  { task: { title: 'А', status: 'in_progress' }, event: 'COMPLETE' },
  { task: { title: 'А', status: 'done' }, event: 'START' },
  { task: { title: 'А', status: 'done' }, event: 'COMPLETE' }
];

for (const item of cases) {
  const before = item.task.status;
  const result = nextTask(item.task, item.event);

  console.log(
    item.task.status,
    '+',
    item.event,
    '-> принято:',
    result.accepted,
    '| стало:',
    result.task.status,
    '| вход после:',
    item.task.status
  );
}
```

| Состояние до | Событие | Принято? | Стало | Вход **после** | Изменился вход? |
|---|---|---|---|---|---|
| `new` | `START` | ? | ? | ? | ? |
| `new` | `COMPLETE` | ? | ? | ? | ? |
| `in_progress` | `START` | ? | ? | ? | ? |
| `in_progress` | `COMPLETE` | ? | ? | ? | ? |
| `done` | `START` | ? | ? | ? | ? |
| `done` | `COMPLETE` | ? | ? | ? | ? |

**Что вы должны увидеть:** в колонке «Вход после» — **всегда** то же, что было в колонке «Состояние до». Ни одна строка не отличается. Это и есть чистота, выраженная **числами**.

### Что означает «одинаковый результат для одинаковых входов»

Вызовите `nextTask()` дважды с **одним и тем же** входом:

```javascript
const first = nextTask({ title: 'А', status: 'new' }, 'START');
const second = nextTask({ title: 'А', status: 'new' }, 'START');

console.log(first.accepted === second.accepted);
console.log(first.task.status === second.task.status);
console.log(first.task.title === second.task.title);
```

Все три строки напечатают `true`. Значит: **одинаковые входные значения → одинаковые значения результата**.

> **Важная оговорка.** Мы сравнивали **значения**: `first.task.status === second.task.status`. Мы **не** сравнивали сами объекты `first.task` и `second.task` — это **разные** объекты (два вызова создали два новых объекта). Совпадение **объектов** по ссылке — это уже **другая** тема, и сегодня она нам не нужна. Мы говорим только о **значениях**: одинаковые входы → одинаковые значения на выходе.

Сравните со старой функцией. Со **старой** `transitionTask()` повторный вызов давал **другой** результат, потому что она смотрела на **уже изменённые** данные:

```javascript
// Старый вариант (Урок 13) — так больше не работает:
// transitionTask(1, 'COMPLETE');   // стало done
// transitionTask(1, 'COMPLETE');   // теперь смотрит на done — другой случай

// Новый вариант — всегда одно и то же:
nextTask({ title: 'А', status: 'new' }, 'START');   // всегда in_progress
nextTask({ title: 'А', status: 'new' }, 'START');   // снова in_progress
```

### Проверка «посторонние задачи не тронуты»

Чистота `nextTask()` — это про **её** аргументы. А что с остальными задачами? Их вообще не касались — но проверим **явно**:

```javascript
const beforeCount = tasks.length;
const beforeFirst = tasks[0].status;
const beforeThird = tasks[2].status;

transitionTask(1, 'COMPLETE');

console.assert(tasks.length === beforeCount, 'Количество задач не должно измениться');
console.assert(tasks[0].status === beforeFirst, 'Первая задача не должна измениться');
console.assert(tasks[2].status === beforeThird, 'Третья задача не должна измениться');
console.assert(tasks[1].status === 'done', 'Выбранная задача должна стать done');
```

> **Заметьте.** Эта проверка — про **приложение**, а не про `nextTask()`. Чистая функция не «не трогает посторонние задачи» — она **вообще не знает** про `tasks`. Посторонние задачи не тронуты потому, что **обёртка** меняет **ровно одну** ячейку массива: `tasks[index] = result.task`.

## Шаг 4. Modify — ломаем чистую функцию по одному пункту (15 минут)

### Зачем мы это делаем

Пока `nextTask()` просто работает, мы **не знаем**, что именно она гарантирует. Сейчас мы **намеренно** сломаем её — по одному пункту — и убедимся, что замечаем.

> **Никаких опасных команд.** Мы **правим текст в редакторе** и **отменяем правку обратно** — вручную. Никаких `git reset`, `git checkout --` и прочих команд, которые могут затереть вашу работу.

### Эксперимент A — случайное изменение (нарушаем чистоту)

**Что делаем.** В `nextTask()` **замените** создание нового объекта в блоке `new` + `START` на **изменение** самого аргумента:

```javascript
  if (task.status === 'new' && event === 'START') {
    task.status = 'in_progress';
    return {
      accepted: true,
      task: { title: task.title, status: task.status }
    };
  }
```

**Что предсказываем.** Функция **перестанет быть чистой**: она изменит объект, который ей передали. Результат (`accepted`, `task`) будет выглядеть **правильно** — а вот **исходная** задача окажется **изменённой**.

**Что делаем.** Обновите страницу, откройте консоль и выполните:

```javascript
const dirtyInput = { title: 'Прочитать главу', status: 'new' };
const dirtyResult = nextTask(dirtyInput, 'START');

console.log('исходная задача:', dirtyInput);
console.log('результат:', dirtyResult.task);
```

**Что наблюдаем.** `исходная задача` напечатается как `{ title: 'Прочитать главу', status: 'in_progress' }` — **изменённая**! При этом `результат` будет `in_progress` — **правильный**. То есть функция вернула **верное** значение, но **испортила** входные данные. Это **не** ошибка ответа, это **ошибка** контракта: чистая функция **не имеет права** менять то, что ей дали.

Проверьте это проверкой:

```javascript
const dirtyInput2 = { title: 'Прочитать главу', status: 'new' };
nextTask(dirtyInput2, 'START');

console.assert(dirtyInput2.status === 'new', 'Исходная задача не должна измениться');
```

`console.assert()` **напишет** сообщение — и это **правильный** результат проверки: контракт чистоты **нарушен**.

| Требование | После эксперимента A | Результат |
|---|---|---|
| Результат правильный по таблице | `in_progress` — правильно | **выполняется** |
| Исходный объект **не изменён** | стал `in_progress` | **ломается** |
| Функция **чистая** | изменяет вход | **ломается** |

> **Верните всё как было.** Уберите строку `task.status = 'in_progress';` и верните создание нового объекта:
>
> ```javascript
>   if (task.status === 'new' && event === 'START') {
>     return {
>       accepted: true,
>       task: { title: task.title, status: 'in_progress' }
>     };
>   }
> ```

### Эксперимент B — неправильный результат (остаёмся чистыми)

**Что делаем.** Верните всё как было. Теперь сделайте так, чтобы **событие `COMPLETE` из состояния `new` принималось**:

```javascript
  if (task.status === 'new' && event === 'COMPLETE') {
    return {
      accepted: true,
      task: { title: task.title, status: 'done' }
    };
  }
```

**Что предсказываем.** Функция останется **чистой** — мы по-прежнему создаём новый объект и ничего не меняем. Но она начнёт **врать**: таблица переходов говорит, что `new` + `COMPLETE` — **отказ**, а функция скажет «принято».

**Что делаем.** Обновите страницу, откройте консоль и выполните:

```javascript
const wrongInput = { title: 'Прочитать главу', status: 'new' };
const wrongResult = nextTask(wrongInput, 'COMPLETE');

console.log('принято:', wrongResult.accepted);
console.log('исходная задача:', wrongInput);
```

**Что наблюдаем.** `принято: true` — а по таблице должно быть `false`. При этом `исходная задача` — по-прежнему `{ …, status: 'new' }` — **не изменилась**. Функция **чистая**, но **неверная**.

| Требование | После эксперимента B | Результат |
|---|---|---|
| Исходный объект **не изменён** | не изменился | **выполняется** |
| Функция **чистая** | чистая | **выполняется** |
| Результат правильный по таблице | `true` вместо `false` | **ломается** |

> **Главный вывод урока.** **Чистота — это не правильность.** Это **два разных** требования, и ломаются они **независимо**:
>
> | | Ответ неверный | Ответ верный |
> |---|---|---|
> | **Функция изменяет вход** | Эксперимент A: **не чистая** | — |
> | **Функция не изменяет вход** | Эксперимент B: **чистая, но неверная** | Норма: **чистая и верная** |
>
> Формулировка, которую стоит запомнить: **чистота не значит «правильно». Правильность не значит «чисто».**

> **Верните всё как было.** Удалите добавленный блок `if` целиком и проверьте, что `new` + `COMPLETE` снова даёт отказ.

### Чек-лист после изменений

| Что | Как проверить | Ожидаемо |
|---|---|---|
| Чистота | `nextTask(obj, 'START')`, потом `obj.status` | `new` — не изменился |
| Шесть переходов | шаг «Таблица наблюдения» | как в таблице переходов |
| Посторонние задачи | `transitionTask(1, 'COMPLETE')` | задачи 0 и 2 прежние |

| Оформление | нажать кнопку темы | переключается как раньше |

## Источники подхода

Урок построен по схеме **PRIMM** (Predict → Run → Investigate → Modify → Make): [primmportal.com](https://primmportal.com/). Шаг Predict учит записывать ожидаемое поведение **до** выполнения; порядок «сначала предсказать, потом запустить» опирается на исследования чтения и трассировки кода новичками (Busjahn & Schulte, 2013; Lister et al., 2004, 2009), перечисленные на странице [Research](https://primmportal.com/research/).

Идея урока — **чистое вычисление рядом с изменяющим состояние**, в его простейшей, наблюдаемой форме: сначала формулируется контракт «что на входе, что на выходе, что не меняется», потом пишется функция, которая этот контракт выполняет, потом контракт **нарушается** намеренно, чтобы убедиться, что он вообще что-то проверяет. Приём «контракт записывается **до** кода» продолжает линию Уроков 12–13. Разделение вычисления и изменения состояния — та же линия, что разделение «операции данных» и «связи с интерфейсом» в Уроке 12: **у разных частей программы — разные обязанности**.

Урок **не** вводит формальных конструкций: ни функций высшего порядка, ни редьюсеров как фреймворка, ни spread-оператора, ни структурного разделения, ни глубокого клонирования, ни персистентных коллекций, ни рекурсии, ни TypeScript, ни классов, ни реактивного программирования. Тот же приём, что и раньше, сохранён: **новое понятие добавляется поверх знакомого кода** — обычные строки, `if` / `else`, функции, массивы, объекты и **возврат объекта из функции**.

Различение **наблюдаемого результата проверки**, **контракта** и **формального доказательства** приведено в [COURSE-OUTLINE.md](COURSE-OUTLINE.md) (Фаза III) и не сводится здесь к «программа доказана». Рассуждение об **эквивалентности значений** (одинаковые входы → одинаковые значения результата) приведено в его **наблюдаемой** форме — через сравнение значений, а не через утверждение об идентичности объектов; формальные доказательства остаются предметом более поздних фаз курса.
