## 3. P1 — Исправление семантики выбора по умолчанию

### Подтверждённый дефект

Имитация `<select>` в `tools/check-lesson-11.mjs` отражала **интерфейс**
свойства `selectedIndex` (позиция с нуля, `-1` — ничего не выбрано), но **не**
воспроизводила **начальное** состояние выбора: `appendChild()` добавлял вариант
и **не** выбирал его.

### Документированное поведение (источники)

| Источник | Формулировка |
|---|---|
| MDN, `HTMLSelectElement.selectedIndex` | *«…the numeric index of the first selected `<option>` element in a `<select>` element, if any, or −1 if no `<option>` is selected.»* |
| MDN, `<select>` (Usage notes) | *«If no selected attribute is specified, the first `<option>` element will be selected by default.»* |
| WHATWG HTML Standard, «The select element», алгоритм «ask for a reset» | Если `multiple` отсутствует, размер отображения равен `1` и ни один вариант не выбран — выбранным становится **первый** не отключённый вариант в порядке дерева |

### Исправление

В `appendChild()` добавлено правило: **пока ни один вариант не выбран,
выбранным становится первый добавленный.**

| Операция | Ожидаемо | Фактически после исправления |
|---|---:|---:|
| Пустой `<select>` | `-1` | `-1` ✅ |
| Добавлен первый вариант | `0` | `0` ✅ |
| Добавлен второй вариант | `0` | `0` ✅ |
| Добавлен третий вариант | `0` | `0` ✅ |
| Явный выбор третьего варианта | `2` | `2` ✅ |
| Явная установка `selectedIndex = -1` | `-1` | `-1` ✅ |
| Очистка всех вариантов | `-1` | `-1` ✅ |
| Повторное заполнение пустого списка | `0` | `0` ✅ |

### Что НЕ моделируется (документировано в коде)

- атрибуты `multiple` и `disabled`;
- placeholder-вариант (первый вариант с пустым значением);
- `<optgroup>` и вложенные `<option>`;
- выбранность, заданная атрибутом `selected` в разметке;
- полный алгоритм «ask for a reset» и синхронизация `selectedIndex`
  с `selectedOptions`/`value`;
- поведение при вставке варианта **в начало** списка.

> **ГРАНИЦА ДОКАЗАТЕЛЬСТВ.** Сверка модели с документацией **НЕ является**
> выполнением в настоящем браузере. Нативное поведение `selectedIndex`
> **не измерялось** — **NOT_EXECUTED**.

### Исполненный отрицательный контроль

**NC-SEL-1** исполняет **прежний** `appendChild()` (не выбирающий первый
вариант) и наблюдает `selectedIndex === -1` после добавления первого варианта.
Контракт «после добавления первого варианта выбран первый» ломается; на
исправленной модели тот же сценарий даёт `0`.

### Ученительская поправка

В `LESSON-11.md` добавлено **одно** примечание: первый вариант выбирается
браузером по умолчанию; пользователь может выбрать другую задачу; `-1` — это
«ничего не выбрано» (пустой список или снятый выбор); **защита по-прежнему
нужна**. Новых элементов управления, placeholder-вариантов и проверок формы не

### Главная модель урока

**Требование → контракт → реализация → проверка.**

Три термина поданы как **три стороны одного контракта**, а не три темы:

| Термин | Смысл в уроке |
|---|---|
| **Предусловие** | Что должно быть верно **до**: вход — целое число, указывающее на существующую задачу |
| **Постусловие** | Что становится верно **после** успеха: у выбранной задачи `done === true` |
| **Инвариант** | Что остаётся нетронутым: состояния остальных задач, названия, количество |

### Разграничение, которое урок проводит явно

| Что | Отличие |
|---|---|
| **Предусловие** | Требование к входу |
| **Защита** | *Обнаружение* нарушения предусловия в коде |
| **Поведение при отказе** | *Определённое* поведение: вернуть `false` и ничего не менять |

Урок прямо говорит: **«не всякая защита — это предусловие»** и **«отказ — не
поломка»**: функция, возвращающая `false` на неверном входе, контракт **не
нарушает** — она его **выполняет**.

### Извлечение операции данных

```javascript
function markTaskDone(index) {
  if (!Number.isInteger(index) || index < 0 || index >= tasks.length) {
    return false;
  }

  tasks[index].done = true;
  return true;
}
```

Урок объясняет `Number.isInteger()` **кратко** и прямо говорит, что это
необязательное упражнение Урока 10 — выполнять его **не требуется**.

Урок **не называет** `markTaskDone()` чистой функцией: сказано, что она
**меняет** `tasks[index].done`, и что полезное разделение — это **операция
данных** против **связи с интерфейсом**, а не функциональная чистота.

## 8. Исполненные отрицательные контроли Урока 12

Каждый контроль **исполняет испорченную реализацию** и наблюдает
**конкретное** нарушение своего контракта. Наличие `notEqual()` само по себе
**не** считается доказательством действенности.

### 16.1. Неточность определения инварианта

**Что было заявлено в этом отчёте (разделы 6, 7, 9 и 11).** Отчёт
описывал **инвариант** Урока 12 как требование «остальные задачи, их
названия и количество остаются прежними» — то есть как «то, что
обязательно не меняется».

**Почему это было неверно.** Это смешивает **два разных** понятия:

| Понятие | Что оно означает |
|---|---|
| **Инвариант состояния** | Свойство данных, которое должно выполняться **всегда**, даже когда значения меняются |
| **Граница допустимых изменений** (условие кадра) | Список того, что операция **не имеет права** менять |

Инвариант запрещает не «изменение», а «сломанное состояние». Значение
может измениться и при этом остаться свойством: `done` меняется с `false`
на `true`, и свойство «`done` — логическое значение» **выполняется**.

**Источники.** Eiffel, *Design by Contract and Assertions* (инвариант —
свойство, выполняющееся всегда, в том числе при изменении значений);
OpenJML, *Frame Conditions* (условие кадра отдельно описывает, какие
части состояния операция вправе изменять).

**Что исправлено (в `LESSON-12.md`).** Урок **не переписан**: его
основной контракт и структура PRIMM сохранены. Исправлены только
**объяснения**:

| Место в уроке | Прежде | Теперь |
|---|---|---|
| «Три стороны одного контракта» | «Инвариант — что операция обязана не тронуть» | «Инвариант — какое свойство обязано остаться в силе», с явным пояснением, что это **не** «ничего не менять» |
| Таблица контракта | семь строк | семь строк **+** строка «Целостность данных» (`done` — логическое значение) и пояснение: постусловие / граница / инвариант — **три разных** требования |
| «Теперь вводим термины» | «Остальные задачи… → Инвариант» | «`done` — логическое значение → **Инвариант состояния**»; «Остальные задачи… → **Граница допустимых изменений** (условие кадра)» |
| Таблица наблюдения | «Инвариант про остальные задачи» | «Граница допустимых изменений», **плюс** отдельная таблица «Инвариант состояния» |
| Эксперимент B | «инвариант про остальные задачи ломается» | «**граница допустимых изменений** ломается», и **показан таблицей**, что инвариант состояния при этом **выполняется** |
| Шаг Modify | два эксперимента (A, B) | добавлен **эксперимент C** — ломается **тип** `done` (`'да'` вместо `true`): ломаются постусловие и инвариант, а граница **выполняется** |

**Что НЕ требовалось от ученика.** Четвёртый формальный термин
**не** добавлен в обязательные требования. «Граница допустимых изменений»
дана **по-русски, обычными словами**, а профессиональное имя «условие
кадра» приведено **как короткое уточнение** («вам его не нужно
запоминать»). Критерий завершения урока по-прежнему требует развести
наблюдаемые требования, а не выучить четвёртое слово.

**Исполненные доказательства (не текстовая проверка).** В
`tools/check-lesson-12.mjs` добавлены тесты `INV-1`, `INV-2`, `INV-2b`,
