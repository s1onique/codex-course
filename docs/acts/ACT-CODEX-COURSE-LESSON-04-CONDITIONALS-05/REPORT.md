## 3. P1 repair evidence

### P1-A — DOM initialization timing

**Старый дефект:** `querySelector()` выполнялся до проверки `document.readyState`; при `readyState === 'loading'` отсутствующие элементы давали `null`, внешний `if` не позволял зарегистрировать `DOMContentLoaded`.

**Исправление:** сохранён один знакомый механизм `readyState`/`DOMContentLoaded`, но оба DOM-lookup перенесены внутрь `startCounter()`. Проверка элементов и подключение обработчика выполняются только после доступности DOM.

**Обязательный negative control (старый код):**

| Шаг | Вход | Наблюдение |
|---|---|---|
| 1 | `readyState = 'loading'` | страница ещё загружается |
| 2 | `#theme-button` и `#counter` отсутствуют при первом выполнении | подтверждено `querySelector(...) === null` |
| 3 | выполнен точный старый блок Урока 03 | `DOMContentLoaded` не зарегистрирован |
| 4 | элементы созданы после выполнения | сценарий продолжается |
| 5 | отправлен `DOMContentLoaded` | старый обработчик отсутствует |
| 6 | нажата тема-кнопка | счётчик не изменился |
| 7 | наблюдение | `counter = 0` — **ожидаемый FAIL старой реализации** |

**Исправленный вариант:** при тех же входах после `DOMContentLoaded` нажатие дало `counter = 1` и ровно **один** счётчиковый обработчик. Контроль с уже разобранным DOM также дал `counter = 1` после одного нажатия.

## 4. P2 duplicate-counter correction

Прежний контракт S2 ошибочно считал рост общего числа click-listener успехом. Новый контракт различает назначения:

- существующий счётчик: ученик идёт по основному пути и **не выполняет fallback**; один счётчиковый обработчик и прежнее поведение сохраняются;
- страница без счётчика: fallback устанавливает **ровно один** счётчиковый обработчик;
- обработчик переключения темы может сосуществовать со счётчиковым, потому что выполняет другое действие.

Это отражено в `LESSON-03.md` и проверено исполненным harness, а не объявлением числа обработчиков.

## 5. Lesson 04 content and learning objectives

`LESSON-04.md` реализует линейный путь:

**существующий счётчик → сравнение → ветка → видимое сообщение → проверка.**

Введены только `true`/`false`, `===`, `!==`, `<`, `>`, `<=`, `>=`, `if` и `else`. Циклы, `switch`, `else if`, promises, классы, TypeScript и новая оснастка не требуются.

Цель: ученик объясняет, почему программа выбирает действие, предсказывает ветку и проверяет оба исхода.

Содержание:

- PRIMM: Predict (0, 2, 3, 4) → Run → Investigate → Modify (порог 5) → Make (необязательно);
- один канонический блок `if (clicks >= 3) { … } else { … }`;
- `#message` рядом с существующим счётчиком;
- предупреждение не добавлять второй обработчик;
- проверка противоположной ветки и значения у границы;
- восстановление исходного порога;
- необязательный `points` Урока 03 прямо исключён из пререквизитов;
- завершающая самопроверка и различение заявления Codex от личного наблюдения.

Объём: около 300 строк Markdown, примерно 1 700 слов. Обязательное упражнение начинается в первых ~100 строках; справочная таблица сравнений дана после первого поведения, а не вместо него. Диагностический fallback — один короткий запрос Codex только для чтения.

1. Реальный браузер не выполнен из-за ограничения среды; остаётся риск различий парсинга/рендеринга, не выявленный JavaScriptCore harness.

3. Оценка когнитивной нагрузки основана на структуре и объёме; реальное время освоения не измерялось.
4. Фраза «больше **или равно**» и таблица операторов могут потребовать дополнительной поддержки отдельному ученику, хотя обе ветви проверяются практикой.
