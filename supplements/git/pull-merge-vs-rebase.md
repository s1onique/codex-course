# Git: чем отличаются `pull --no-rebase`, `pull --rebase` и `pull --ff-only`

**Дополнительный материал к [уроку 0](../../LESSON-00.md)**  
**Уровень:** начинающий · **Время:** 10–15 минут  
**Когда пригодится:** в установщике Git for Windows на экране **Choose the default behavior of `git pull`**.

> **Что выбрать сейчас?** Для первых упражнений оставьте **Merge** (как на скриншоте). Git не будет переписывать уже существующие локальные коммиты. **Rebase** изучим позже. **Fast-forward only** — хороший строгий режим, но если истории разойдутся, он остановится и потребует решения от человека.

## 1. Зачем вообще нужен `git pull`?

Представьте, что у проекта есть две копии:

- **На GitHub** — версия, доступная через интернет.
- **На вашем компьютере** — локальная версия, с которой работаете вы и Codex.

Допустим, вы изменили текст на компьютере, а кто-то другой изменил его на GitHub. Как объединить эти изменения?

Команда `git pull` сначала **получает новые коммиты** (`git fetch`), а затем **включает их в текущую ветку**. Вот способ этого второго действия и выбирается в установщике.

**Коммит (commit)** — сохранённый шаг в истории проекта: какие изменения были сделаны и кем.

Это не то же самое, что `git push`: **pull получает** изменения, а **push отправляет** ваши коммиты на GitHub.

## 2. Когда все три варианта работают одинаково

Допустим, на вашем компьютере история закончилась на коммите `B`, а на GitHub уже появился `D`:

```text
Компьютер:   A---B
GitHub:      A---B---D
```

Вы запускаете `git pull`. Git просто продвигает вашу ветку вперёд:

```text
Компьютер:   A---B---D
GitHub:      A---B---D
```

Это называется **fast-forward** («перемотка вперёд»).

**Здесь Merge, Rebase и Fast-forward only дают одинаковый результат.** Новый объединяющий коммит не нужен, потому что истории не разошлись.

## 3. Когда появляется разница: обе копии изменились

Теперь предположим:

- Вы сохранили у себя коммит `C` (например, изменили заголовок).
- На GitHub независимо появился коммит `D` (например, добавили описание).

```text
                 C  ← ваш компьютер
                /
      A---B----+
                \
                 D  ← GitHub
```

Коммиты `C` и `D` появились **независимо друг от друга**. Это называют **расхождением истории** (*divergence*).

Теперь Git нужно решить, как совместить две линии изменений.

## 4. Вариант Merge: соединить обе истории

На экране установщика: **Merge**.  
Команда для разового использования:

```powershell
git pull --no-rebase
```

Git сохраняет оба исходных коммита (`C` и `D`) и при успешном объединении создаёт **ещё один коммит `M`**, который связывает обе ветви истории:

```text
      A---B---C-----M  ← ваш компьютер
           \       /
            D-----/    ← коммит с GitHub
```

`M` — *merge commit* («коммит объединения»).

**Преимущество:** история не переписывается. Можно увидеть, что работа велась параллельно и затем была объединена.

**Недостаток:** если такие объединения делать часто, история становится более разветвлённой.

**Аналогия:** две версии документа не заменяют друг друга, а соединяются в новую версию, сохраняя информацию об обеих.

## 5. Вариант Rebase: переставить свои изменения поверх новых

На экране установщика: **Rebase**.  
Команда:

```powershell
git pull --rebase
```

Git сначала учитывает `D` с GitHub, а затем **повторно применяет ваш коммит `C` поверх него**:

```text
      A---B---D---C'  ← ваш компьютер
```

Почему `C'`, а не `C`? Потому что Git создал **новый коммит** с новым идентификатором. Это не просто перемещение старого коммита.

**Преимущество:** получается прямая, более простая для чтения история без дополнительного merge-коммита.

**Недостаток:** меняются идентификаторы ваших локальных коммитов. Если такие коммиты уже были опубликованы и на них опирается другой человек, это может создать серьёзную путаницу.

**Аналогия:** вы переписываете свою запись в дневнике так, будто сделали её *после* новой записи коллеги. Содержание стараетесь сохранить, но это уже другая запись.

> **Главное правило для новичка:** не переписывайте через rebase коммиты, которыми уже поделились с другими людьми, без предварительного согласования.

## 6. Вариант Fast-forward only: только если объединять ничего не нужно

На экране установщика: **Fast-forward only**.  
Команда:

```powershell
git pull --ff-only
```

- Если у вас не было собственных новых коммитов, а на GitHub появились изменения — Git скачает и применит их.
- Если история разошлась, как в примере с `C` и `D`, — **Git остановится с ошибкой**. Он не выберет Merge или Rebase за вас.

**Преимущество:** Git не выполняет неожиданное объединение и не переписывает историю автоматически.

**Недостаток:** при расхождении придётся понять проблему и выбрать способ объединения вручную.

Это хороший вариант, когда вы уже немного освоились с Git и хотите принимать такие решения явно.

## 7. Сравнение в одной таблице

| Что происходит | Merge | Rebase | Fast-forward only |
|---|---|---|---|
| Только GitHub получил новые коммиты | Перемотка вперёд | Перемотка вперёд | Перемотка вперёд |
| Новые коммиты есть и там, и там | Объединяет истории | Переносит ваши коммиты поверх новых | Останавливается |
| Появится новый merge-коммит | Да, при расхождении | Нет, в простом случае | Нет |
| Изменятся ID ваших локальных коммитов | Нет | Да, при повторном применении | Нет |
| Подходит для первой установки | **Да — рекомендуем** | Пока не нужно | Можно, но сложнее при ошибке |

**Важное замечание:** при Merge *и* при Rebase бывают **конфликты**, когда Git не знает, какую из несовместимых правок оставить. Ни один вариант не гарантирует, что всё объединится автоматически.

## 8. Что делать при конфликте?

**Конфликт** — это не уничтожение проекта. Git сообщает, что ему нужна помощь человека: например, две разные версии изменили одну и ту же строку.

Если это ваш первый конфликт:

1. **Не угадывайте** и не удаляйте файлы.
2. Выполните `git status`, чтобы увидеть, что происходит.
3. Покажите сообщение Codex или преподавателю.
4. Если хотите отказаться от незаконченного объединения, обычно можно вернуться к состоянию до операции:

После Merge:

```powershell
git merge --abort
```

После Rebase:

```powershell
git rebase --abort
```

Эти команды применимы **во время соответствующей незавершённой операции**. Не запускайте их наугад: сначала посмотрите `git status`.

**Не используйте `git push --force` для «исправления» конфликта.** Это другая, потенциально опасная операция.

## 9. Какой вариант выбрать именно в этом курсе?

На экране **Git 2.56.1 Setup → Choose the default behavior of `git pull`**:

**Оставьте выбранный `Merge` и нажмите `Next`.**

Почему:

- Сейчас задача — установить Git и открыть свой репозиторий в Codex.
- На первых уроках не требуется переписывать историю коммитов.
- На примерах позже легче увидеть и объяснить, как Git объединяет две ветви.

Этот выбор **не навсегда**. Можно изменить настройку без переустановки Git. Кроме того, при каждом вызове команды можно явно указать `--no-rebase`, `--rebase` или `--ff-only`.

Кстати, точная команда для пункта **Merge** — `git pull --no-rebase`, **не** `git pull --merge`.

## 10. Проверьте себя

1. На GitHub появился новый коммит, а у вас своих новых коммитов нет. Будет ли разница между Merge и Rebase?
2. Почему после Rebase коммит `C` становится `C'`?
3. Какой вариант остановится, если новые коммиты появились и на компьютере, и на GitHub?
4. Означает ли надпись «конфликт», что все файлы потеряны?
5. Нужен ли Rebase, чтобы выполнить первый урок Codex?

**Ответы для самопроверки:** 1) Нет, будет fast-forward. 2) Его создали заново поверх изменившейся истории. 3) Fast-forward only. 4) Нет. 5) Нет.
