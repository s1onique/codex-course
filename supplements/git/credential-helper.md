# Git: что такое Credential Helper и зачем нужен Git Credential Manager?

**Дополнительный материал к [уроку 0](../../LESSON-00.md)**  
**Уровень:** начинающий · **Время:** 15–20 минут  
**Когда читать:** на экране установки Git for Windows с вопросом **Choosing the credential helper**.

> **Короткий ответ:** выберите **Git Credential Manager** и нажмите **Next**. Он поможет Git безопасно войти в GitHub через браузер и запомнить данные доступа, чтобы не проходить авторизацию при каждом `git push`.

## 1. Зачем Git нужно входить в GitHub?

Давайте сначала вспомним: **Git** — программа на вашем компьютере, а **GitHub** — сайт, где хранится удалённая копия проекта.

Вы можете создать коммит на компьютере без интернета. Но для некоторых действий с GitHub необходимо подтвердить, кто вы и какие права у вас есть.

| Действие | Нужно ли входить в GitHub? |
|---|---|
| `git status` — посмотреть локальные изменения | **Нет** |
| `git commit` — сохранить локальную историю | **Нет** |
| `git clone` — скачать публичный проект по HTTPS | Обычно **нет** |
| `git clone` — скачать приватный проект по HTTPS | **Да** |
| `git pull` — получить изменения приватного проекта по HTTPS | **Да** |
| `git push` — отправить изменения в свой репозиторий по HTTPS | **Да** |

Для доступа важны две вещи:

1. **Аутентификация:** доказать, что вы вошли в свой аккаунт GitHub.
2. **Авторизация:** проверить, разрешено ли этому аккаунту читать или изменять *конкретный репозиторий*.

Даже если вы успешно вошли в GitHub, это **не даёт права изменять чужой репозиторий**.

## 2. Credential Helper — «помощник по входу»

Представьте, что вы приходите в здание с электронным пропуском. Git хочет пройти через дверь, а Credential Helper отвечает за получение пропуска и его безопасное хранение.

```text
Вы: «Git, отправь мои изменения на GitHub»
             |
             v
Git: «Мне нужно подтвердить доступ»
             |
             v
Credential Helper: «Проверю, есть ли действующий пропуск»
             |
             +--- Есть действующий пропуск ---> использует его
             |
             +--- Нет пропуска ---> предлагает авторизоваться
                                      через GitHub в браузере
             |
             v
GitHub: «Доступ разрешён?»
             |
             +--- Да ---> Git выполняет операцию
             |
             +--- Нет --> Git показывает ошибку
```

**Credential Helper** — общее название механизма Git. Разные программы могут выступать такими помощниками.

**Git Credential Manager (GCM)** — конкретная программа, которую предлагает установщик Git for Windows. Она поддерживает авторизацию через браузер и безопасное хранилище операционной системы.

## 3. Что происходит при первом входе

Предположим, вы склонировали публичный репозиторий и позже хотите отправить изменения:

```powershell
git push
```

Если у Git ещё нет сохранённых данных доступа, возможна такая последовательность:

1. Git обращается к Git Credential Manager.
2. GCM показывает окно авторизации и предлагает открыть браузер (или другой поддерживаемый способ входа).
3. В браузере вы входите в **github.com**, если ещё не вошли.
4. GitHub может попросить подтверждение двухфакторной аутентификации (2FA) и разрешение приложению на доступ. **Прочитайте, кто запрашивает разрешение и какие права ему нужны.**
5. После успешного входа GCM получает подходящий *токен доступа*, а не ваш пароль от GitHub.
6. GCM сохраняет необходимые данные в защищённом хранилище Windows и предоставляет их Git при последующих операциях.
7. Git выполняет `push`, если у аккаунта есть права на репозиторий.

**Что такое токен?** Это специальный цифровой пропуск, которым программа подтверждает своё право обращаться к сервису. Токен может истечь, быть отозван или иметь ограниченные права. Это не то же самое, что пароль от аккаунта.

> Для упражнений курса **не нужно вручную создавать Personal Access Token (PAT)**, пока Git Credential Manager успешно работает с GitHub.

**Почему окно не появилось во время `git clone`?** Публичные репозитории обычно можно скачивать без авторизации. Первый запрос на вход может возникнуть позже — например, при `git push`.

## 4. Где именно хранятся данные?

Здесь легко запутаться из-за двух похожих названий:

| Название | Что делает |
|---|---|
| **Git Credential Manager** | Программа-помощник: организует вход и получает/выдаёт Git данные доступа. |
| **Windows Credential Manager** | Системное хранилище Windows, в котором GCM по умолчанию сохраняет данные доступа. |

На Windows 10 стандартный GCM обычно использует **Windows Credential Manager**. Это лучше, чем записывать токен в обычный текстовый файл проекта или в строку команды.

Чтобы посмотреть **наличие** сохранённых записей:

1. Откройте меню **Пуск** и найдите **Диспетчер учётных данных** / **Credential Manager**.
2. Перейдите в **Учётные данные Windows** / **Windows Credentials**.
3. После успешного входа в GitHub там *может* появиться запись для Git/GitHub. Название записи зависит от версии и настройки.
4. **Не открывайте, не копируйте и никому не отправляйте значения паролей или токенов.** Для обучения достаточно знать, что запись существует.

Это не означает абсолютной защиты: вредоносная программа, получившая доступ к вашему сеансу Windows, может попытаться воспользоваться вашими полномочиями. По этой причине полезны отдельная учётная запись Windows, блокировка компьютера и обновления безопасности.

## 5. Что НЕ делает Credential Helper

Он **не**:

- сохраняет историю проекта — этим занимается Git;
- автоматически отправляет коммиты — `git push` по-прежнему нужно запустить;
- создаёт вам аккаунт GitHub;
- предоставляет права на чужие репозитории;
- хранит ваш пароль GitHub в `README.md` или `.git`;
- заменяет пароль Windows или пароль ChatGPT;
- обслуживает SSH-ключи, если репозиторий подключён по SSH, а не HTTPS.

**Важно для Codex:** установленный на вашем Windows-компьютере Git может пользоваться этим помощником, когда выполняет локальные Git-команды по HTTPS. Но авторизация в *облачном* Codex — отдельная история: Windows Credential Manager на её компьютере не становится автоматически доступным облачному сервису.

## 6. HTTPS и SSH — два способа подключения

Один и тот же репозиторий на GitHub можно подключить разными способами:

```text
HTTPS:  https://github.com/USERNAME/REPOSITORY.git
SSH:    git@github.com:USERNAME/REPOSITORY.git
```

- **HTTPS + Git Credential Manager:** наиболее понятный вариант для начала; вход в GitHub обычно происходит через браузер.
- **SSH:** использует отдельную пару ключей и соответствующую настройку. GCM не управляет SSH-ключами.

**Для этого курса выбираем HTTPS.** Это не делает SSH плохим — просто сейчас не нужно осваивать два механизма авторизации одновременно.

## 7. Почему нельзя просто указать пароль GitHub?

GitHub больше **не принимает пароль аккаунта** для Git-операций через HTTPS. Используются токены или другие поддерживаемые методы, в том числе вход через Git Credential Manager.

**Опасная идея:** «Добавлю токен прямо в адрес репозитория или в файл, чтобы всё работало». Не делайте так. Токен может оказаться в истории команд, логах, настройках или файлах репозитория.

Альтернатива, которую мы **не рекомендуем**:

```text
credential.helper=store
```

У Git есть помощник `store`, сохраняющий данные доступа в **незашифрованном текстовом файле**. Он работает, но для обычного компьютера с Git Credential Manager это плохой компромисс по безопасности.

## 8. Имя автора коммита — не данные для входа

В уроке 0 мы выполняли:

```powershell
git config --global user.name "Имя или ник"
git config --global user.email "адрес@example.com"
```

Это **подпись автора коммита**, а не вход в GitHub. Можно указать чужое имя в этой настройке, но это не предоставит доступ к чужому аккаунту.

**Git Credential Manager** решает другую задачу — подтверждение прав на удалённый сервер.

## 9. Как проверить настройку без раскрытия секретов

Откройте **PowerShell** и выполните:

```powershell
git --version
git credential-manager --version
git config --show-origin --get-all credential.helper
```

Что означают ответы:

- `git --version` — Git установлен.
- `git credential-manager --version` — команда GCM доступна.
- `git config ... credential.helper` — какие помощники Git настроены и откуда пришли настройки.

В результате может быть `manager` либо путь/команда, запускающая GCM. **Не нужно вручную менять настройки, если вход через браузер уже работает.** Если значение отсутствует или отличается, сначала уточните, что установлено; не копируйте непонятные команды из интернета.

Проверить тип подключения внутри папки проекта можно так:

```powershell
git remote -v
```

Если адрес начинается с `https://`, здесь подходит GCM. Если с `git@github.com:`, используется SSH.

**Не запускайте для «проверки» команды, печатающие сохранённый токен на экран** (например, прямые низкоуровневые запросы `git credential fill`). Это секрет.

## 10. Если что-то пошло не так

| Проблема | Возможная причина и что делать |
|---|---|
| GitHub не просит войти при `clone` | Репозиторий публичный — это нормально. |
| При `push` открывается окно браузера | Так GCM получает разрешение на работу. Проверяйте адрес сайта и запрошенные права. |
| `Authentication failed` | Сохранённый токен мог истечь, быть отозван или относиться к другому аккаунту. |
| `Repository not found` | Проверьте URL, существование репозитория и права аккаунта. |
| `403 Forbidden` | Вы могли успешно войти, но **не иметь права** на конкретную операцию. Повторный вход не всегда решит проблему. |
| Git каждый раз просит войти | Проверьте настройку помощника, тип URL и наличие записи в Windows Credential Manager. |
| GitHub открылся не под тем аккаунтом | Проверьте, в какой аккаунт вошли в браузере, и соответствующие сохранённые данные GCM. |

Если подозреваете неправильные или устаревшие данные доступа, их можно удалить в **Диспетчере учётных данных Windows**: найдите запись, относящуюся к **Git/GitHub**, убедитесь, что это именно она, и удалите *только её*. При следующем доступе Git может попросить войти заново. **Не удаляйте все записи Windows.**

Отдельно можно отозвать доступ приложения в **GitHub → Settings → Applications** (проверьте разделы авторизованных OAuth Apps и GitHub Apps). Удаление локальной записи и отзыв разрешения на стороне GitHub — **не одно и то же**.

## 11. Проверьте себя

1. Зачем Git нужен помощник для входа, если вы уже настроили `user.name` и `user.email`?
2. Почему при клонировании публичного проекта окно GitHub может не появиться?
3. Где GCM обычно сохраняет данные доступа на Windows 10?
4. Можно ли с помощью GCM получить право на чужой приватный репозиторий?
5. Что изменится, если вы используете SSH вместо HTTPS?
6. Что безопаснее: сохранить токен в обычном текстовом файле или позволить GCM использовать хранилище Windows?

**Ответы:** 1) Имя/email — авторство коммитов, а не разрешение сервера. 2) Публичное чтение не требует входа. 3) Windows Credential Manager. 4) Нет. 5) Вход по SSH-ключам, не через GCM. 6) GCM с системным хранилищем.
